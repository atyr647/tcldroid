# Upstreaming Tk for Android

The Android backend is meant to be contributed to Tk. This page is the state of that work: what the patch
series is, how it is kept honest, and what still stands between it and a submission.

## The series (`upstream/series/`)

Five patches against pristine Tk 9.0.4, one concern each, as `git format-patch` output (generated by
`tools/upstream/make_series.py`, which makes real commits so the messages and diffs are what a reviewer sees):

| Patch | What it does |
| --- | --- |
| 0001 `tkPort.h` | Adds `TK_ANDROID` (set for `__ANDROID__`) and includes `tkAndroidPort.h`. Android takes the same stub-declaration section as macOS, because like macOS and Windows it implements Tk's Xlib API in-process. |
| 0002 generic includes | At the 10 places where generic code chooses `tkWinInt.h` / `tkMacOSXInt.h` / `tkUnixInt.h` (and `default.h`), adds the Android case. About 40 lines. |
| 0003 `tkWindow.c` | Destroys every window explicitly on Android, as it already does on Windows and macOS. Found by AddressSanitizer on `window.test`. |
| 0004 `tk.tcl` | Sources `library/android.tcl` when the Android layer is present. No effect elsewhere. |
| 0005 `android/` | The platform itself: ~7,000 lines of C in `android/`, plus `library/android.tcl` and `a11y.tcl`. Nothing in `generic/` changes. |

Patches 0001-0004 are what the development build applies (`upstream/patches/`); `tools/upstream/verify_series.sh`
applies the whole series to a pristine tarball and checks the result is **identical** to the tree that the
tests run on, so the submission cannot drift from what is tested.

## The evidence a maintainer can check

- Tk's own test suite, 97 files, 9,742 tests: 8,445 pass; the 334 failures are each triaged with a reason
  (about 230 test X11 behaviour that has no Android equivalent) and checked on every run; 0 crashes;
  0 AddressSanitizer errors. [tk-test-suite.md](tk-test-suite.md).
- Real-application trials (a 3,000-line Tk course app, all 78 lessons driven through its UI).
- Device runs on a phone (see [status.md](status.md)).

## What is not upstream-ready yet (honest list)

1. **Stub tables.** The Android section reuses the macOS one (`MAC_OSX_TCL`). The right form is a dedicated
   `android` platform tag in `generic/tkInt.decls`, which needs `tools/genStubs.tcl` (a *Tcl* repository file)
   to learn the tag: a small Tcl-side change that would go in with a TIP. Until then extensions compiled against
   Android get macOS's Xlib stub layout, which is correct but implicit.
2. **Build system.** Tk's `unix/configure` has no Android target. This repository builds with the NDK from a
   script. Upstream would want a `--with-tkwin=android` or a documented cross-build, plus an `android/Makefile.in`.
3. **A TIP.** A new platform is a Tcl Core Team decision. The description in [adr/0002](adr/0002-tk-backend-architecture.md)
   and `android/README.md` is the starting text.
4. **Tests in Tk's format.** The Android-specific tests (touch, clipboard, gestures, accessibility, dialogs) are in
   `tests/tk/*.tcl` and run by this repository's scripts; they should become `tests/android.test` in tcltest form.
5. **Licence and copyright.** Tk is BSD-style and contributions to it are made under that licence with the contributor's
   own copyright; this repository is MIT-licensed (`LICENSE`), compatible with that, and the code offered upstream is offered under Tk's licence.
6. **Host side.** The Java host (Activity, JNI, `Paint` text engine) is intentionally not part of Tk; the contract is
   `android/tkAndroid.h`. Upstream needs a minimal reference host or the documented interface only.

## Keeping it in step

`tools/upstream/make_series.py` regenerates the series from the sources here; `tools/upstream/verify_series.sh`
fails if the committed series is stale or differs from the tested tree. Both run in CI.
